## 1. 商店刷新的完整权重链

### 1.1 档位权重（未归一化）—— `rawTierWeights(tilt, run)`

```js
p            = rerollTilt(paid, run)
             = SHOP.rerollTiltGrowth ^ ( min(SHOP.rerollTiltCap, paid × tiltRateMul(run)) / 10 )
             = 1.20 ^ (min(50, paid × E12加速) / 10)          // paid=0 → 1.0；paid=50 → 2.48832
boost        = rarityBoostOf(run)   // 天命所归 C51：common = 0.5^n，epic = legend = 2^n
legendFactor = legendWeightFactor(run)
             = 0.88 ^ (本局已拥有的传奇条数)  ×  (所有 repeatable 传奇都到手 ? 0.35 : 1)
legendMul    = (LEGEND_BASE_WEIGHT / RARITY_WEIGHTS[3]) × legendFactor × boost.legend
             = (2.2 / 3) × legendFactor × boost.legend

w[0] 普通 = 66 × boost.common × p^0
w[1] 稀有 = 21 ×               p^1
w[2] 史诗 = 10 × boost.epic  × p^2
w[3] 传奇 =  3 × legendMul   × p^3  =  2.2 × legendFactor × boost.legend × p^3
```

| 参数 | 值 | 位置 |
| --- | --- | --- |
| `RARITY_WEIGHTS` | `[66, 21, 10, 3]` | `tower-data.js:1278` |
| `LEGEND_BASE_WEIGHT` | 2.2（传奇实际基准，取代表里的 3） | `tower-data.js:441` |
| `LEGEND_HOLD_PENALTY` | 0.12 → 每拥有一条传奇 ×0.88 | `tower-data.js:442` |
| `LEGEND_ALL_OWNED_PENALTY` | 0.35（所有 repeatable 传奇到手后） | `tower-data.js:443` |
| `SHOP.rerollTiltGrowth` / `rerollTiltCap` | 1.20 / 50 | `tower-data.js:297-298` |
| 战斗奖励固定倾斜 | `CHOICE_TILT_PAID = 10` → p = 1.20 | `tower.js:2105` |
| 铸币商店基准 | `MINT_SHOP.tiltPaid = 40` → p = 1.2⁴，普通档再 ×0.4 | `tower-data.js:306-322` |
| `E12 时来运转` | `tiltRateMul = 1 + (2−1)×n` | `tower-data.js:406-411` |

### 1.2 动态档位权重 —— `dynamicTierWeights(baseTier, run, 可用候选)`

```js
effTier[r] = w[r] × ( Σ_{b∈可用(r)} m_b ) / |可用(r)|        // 档内平均倍率
m_b        = shopWeight(b) × repeatWeight^已拥有份数 × (1 / n)   // 后两项即「动态惩罚」
             n = weightDivBy === 'enchanted' ? (附魔数 + weightDivOffset) : 已获得份数
```

默认 `TIER_AVG_INCLUDES_STATIC = false`：**档位平均只用动态惩罚**，静态 `shopWeight` 只影响档内挑谁。

### 1.3 最终每一格

```js
P(档 r)      = effTier[r] / Σ effTier
P(b | 档 r)  = m_b^full / Σ_{c∈可用(r)} m_c^full      // m^full = shopWeight × 动态惩罚
P(b)         = P(档 r) × P(b | 档 r)
```

可用候选 = `pool` 里 `ownable(run,b) && poolFilter(run,b)` 的那些（见 §3 的坑）。

## 2. 各场景的传奇出率（试炼商店，5 格一页）

| 场景 | 已拥有传奇 | legendWeightFactor | 可用传奇 | 单格 P(传奇档) | 一页 ≥1 传奇 |
| --- | --- | --- | --- | --- | --- |
| 全新局（tilt=1） | 0 | ×1.0000 | 5 | **2.2177%** | 10.6077% |
| 战斗奖励基准（tilt=1.2） | 0 | ×1.0000 | 5 | **3.4749%** | 16.2082% |
| 刷到倾斜封顶（50 币 → p=2.488） | 0 | ×1.0000 | 5 | **15.834%** | 57.764% |
| 已拥有 3 条传奇 | 3 | ×0.6815 | 3 | 1.5221% | 7.3822% |
| 试炼池 5 条全到手 | 5 | ×0.5277 | 3（C14/C37/C49） | 1.1828% | 5.7756% |

| **同上 + 保底触发**（见 §4） | 9 | ×0.1108 | 2 | **≈0.83%（1/120）** | — |

> `legendWeightFactor` 明细：0 条 1.0000 / 1 条 0.8800 / 2 条 0.7744 / 3 条 0.6815 / 5 条 0.5277 / 9 条 0.3165，再乘「全部可重复传奇到手」的 0.35 → **0.1108**。

铸币商店（5 件 / 页，基准 `tiltPaid=40`、普通档 ×0.4）：全新局 **14.80%/格**（一页 55.1%）；传奇全到手 **1.89%/格**（一页 9.09%）。

### 2.1 结论（2026-10 之后：有保底了）

- §3 的 `ownable` 问题修好 + C49 去掉次数上限之后，**传奇档永远不会变成空档**：
  `C37`、`C49` 都是 `repeatable` 且可无限获得，所以自然出率不会再归零；
  最坏（C14 也叠满）时剩 C37+C49 两条，自然出率 **0.0478%/格**（一页 0.24%）——比早期低约 46 倍。
- **地板由传奇保底负责**（§4）：最坏情况下每 120 格必出一传奇 ≈ **0.83%/格**，即保底把 0.048% 抬到 0.83%（×17）。

## 3. ✅ 已修：`repeatable` 曾被 `ownable()` 挡掉（2026-10）

`poolFilter()` 里有 `if (hasTag(buff,'repeatable')) return true;`（`tower.js:2098`），
但**真正的抽取口子还要过 `ownable()`**（`rollShopSlots` / `rollChoices` / `rollMintSlots` 都是 `ownable && poolFilter`），
而 `ownable()` 里没有 repeatable 分支 —— 于是「可重复获得」的增益拥有 1 份之后就**再也刷不到**：

| 增益 | 稀有度 | 卡面/标签口径 | 拥有 1 份后 |
| --- | --- | --- | --- |
| E14 讨价还价 | 普通 | 「可重复获得，叠加后不会作用于同一件商品」 | `ownable=false` ❌ |
| C52 涌泉烙印 | 稀有 | `repeatable` | `ownable=false` ❌ |
| C36 挥金如土 | 传奇 | `repeatable`（可无限累计）→ **2026-10 已改成「一局一次、不可叠加」** | `ownable=false` ✅（现在是一局一次的正常行为） |
| C37 虚空铭文 | 传奇 | 「每多附魔一个，再出现的概率就低一档」 | `ownable=false` ❌ |
| C49 终焉烙印 | 传奇 | `repeatable` + `unlimitedStacks` | `ownable=true` ✅（2026-10 已移除次数上限，见 §6） |
| C51/E07/E08/E11 | — | `oncePerRun` | `poolFilter=false` ✅（一局一次，正确） |

**影响**：

1. **C37 的 `weightDivBy: 'enchanted'` 永远不会触发第二次** —— 抽到第一张之后它就从池里消失了，
   「越附魔越难看到」这条机制在实际游戏里根本不成立（这也解释了「降了权重却看不到效果」的另一半原因）。
2. C52 涌泉烙印的重复叠层、E14 讨价还价的多次对折都被同一处挡掉
   （C36 挥金如土已按用户口径改成「一局一次」，不再需要重复获得）。
3. 传奇池会塌缩成 `{C14(2 层), C49(3 份)}`，然后归零（§2.1）。
4. 需求58 的「虚空铭文可重复拾取」测试只断言了 `poolFilterOf`，没断言 `ownableOf`，所以一直是绿的。

**已落地的修法**（`ownable()` 里即时类分支之后）：

```js
/* 带 repeatable 标签的靠 maxStacks / 动态惩罚控量，不靠「同名唯一」。 */
if (D().hasTag(buff, 'repeatable')) return true;
```

修好之后：`E14/C37/C52` 都能重复获得（`C36` 已按用户口径改成「一局一次」，
`C51/E07/E08/E11` 这类 `oncePerRun` 仍由 `poolFilter` 拦住）；
`C37` 永远留在池里（自惩罚随附魔数增长），传奇档不会再变成 0。
回归：`tools/test-fixes-round.cjs` 需求98 ①。

## 4. 如果加保底：三种等价实现

| 方案 | 公式 | 效果 | 代价 |
| --- | --- | --- | --- |
| **A 档位软地板** | `effTier[3] ← max(effTier[3], floor × (effTier[0]+effTier[1]+effTier[2]) / (1 − floor))` | 任意削法下**每格传奇占比 ≥ floor**（floor=1% → 一页 ≥4.9%） | 后期传奇会明显变多；`floor` 需要按层数或「已拥有数」分档才不至于泛滥 |
| **B 计数硬保底** ✅ **已实现** | 见 §4.1 | 最坏「120 格必出一传奇」＝每格 ≥0.83%；早期只 +7.3% | 已加 `run.legendPity`（随存档保留、跨层不清零） |
| **C 惩罚封顶** | `legendWeightFactor ← max(0.35, …)`；`weightDivBy` 的除数封顶（如最多 ÷5） | 把现在 0.2506% 的地板抬到指定值，改动最小 | 治标：全传奇到手时**仍然只有 C14/C49 两条可抽**，且 C37 依旧不回到池里（除非同时修 §3） |

### 4.1 已实现的 B 方案（`TowerData.LEGEND_PITY.slots = 120`）

> 2026-10：C36 挥金如土改成「一局一次、不可叠加」，走到极端时它已经在身上、根本不在池里；
> C49 终焉烙印也**去掉了次数上限**（见 §6），所以极端情况的可用传奇恒为 **C37 + C49**，
> 保底按权重 1 : 2 稳定给出 **1/3 : 2/3** —— 不会像以前那样「拿满 3 次之后只剩 C37」。

```js
// 每一格（试炼商店的每一格货架 + 战斗奖励的每一个选项，铸币商店不算）：
legendPity++;
if (legendPity >= LEGEND_PITY.slots) → 这一格强制走传奇档
  档内挑谁：按 mods.pityWeight 加权（缺省 1，0 = 不进保底池），**忽略 shopWeight / ÷n 等自惩罚**
掷到传奇（自然或保底都算）→ legendPity = 0
传奇池为空时 → 不累加（不空转）
```

保底池的组成（`pityWeight`）：

| 增益 | pityWeight | 说明 |
| --- | --- | --- |
| C37 虚空铭文 | **1** | 1/3 |
| C49 终焉烙印 | **2** | 2/3 |
| ~~C36 挥金如土~~ | **0** | 运营向 + 一局一次（拿到就不在池里了）；`pityWeight: 0` 是第二道保险 |
| 其它传奇（C14/C51/C31/E15/C53/C55） | 1（缺省） | 未到手时也会出现在保底池里 |

于是**「传奇全部拿完」的极端情况下，保底给出的分布正好是 1/3 C37 + 2/3 C49**
（实测 1200 次：C37 34.6% / C49 65.4%，只有这两种可能；回归见需求98 ④）。

计数语义：`legendPity` = **距离上一格传奇过了多少格**（跨层不清零；换局从 0 开始）。

### 4.2 `slots` 的取舍（`LEGEND_PITY.slots`，唯一旋钮）

| slots | 早期等效出率（自然 2.2177%/格） | 极端等效出率（自然 0.2506%/格） |
| --- | --- | --- |
| 40 | 3.745%/格（**+68.9%**） | 2.624%/格（×10.5） |
| 60 | 2.998%/格（+35.2%） | 1.793%/格（×7.2） |
| 80 | 2.660%/格（+19.9%） | 1.378%/格（×5.5） |
| **120（当前）** | **2.379%/格（+7.3%）** | **0.964%/格（×3.8）** |
| 200 | 2.243%/格（+1.1%） | 0.635%/格（×2.5） |

> 三个方案不冲突：现在是 **B**；若还想让「传奇档的整体份额」本身有下限，可再叠 A（软地板）；
> C（惩罚封顶）只影响自然出率，不影响保底。

## 5. 复算方式

```js
// 照 tools/test-fixes-round.cjs 的 setup() 载入之后：
const TD = c.TowerData, T = c.Tower;
const run = T._debugRun('endless');
const cands = TD.shopPool.filter((b) => T.ownableOf(run, b) && T.poolFilterOf(run, b));
const base = TD.rawTierWeights(TD.rerollTilt(0, run), run);   // 未归一化档位权重
const eff = T.dynamicTierWeightsOf(run, cands, base);          // 动态后的档位权重
const share = eff.map((v) => v / eff.reduce((a, b) => a + b, 0));
// share[3] 就是「单格出传奇档」的概率；一页 ≥1 = 1 - (1 - share[3]) ** 5
TD.legendWeightFactor(run); TD.legendOwnedCount(run); TD.allRepeatableLegendsOwned(run);
```

| 想改什么 | 位置 |
| --- | --- |
| 各档基础比例 | `RARITY_WEIGHTS = [66,21,10,3]` |
| 传奇整体压低 | `LEGEND_BASE_WEIGHT`(2.2) / `LEGEND_HOLD_PENALTY`(0.12) / `LEGEND_ALL_OWNED_PENALTY`(0.35) |
| 刷新倾斜 | `SHOP.rerollTiltGrowth`(1.20) / `rerollTiltCap`(50) / E12 的 `tiltRateMul` |
| 单条增益的自惩罚 | 数据里的 `repeatWeight` / `weightDivBy` + `weightDivOffset` |
| 动态权重总开关 | `TIER_DYNAMIC_WEIGHTS`（false = 回到旧的「先摇档再档内抽」） |
