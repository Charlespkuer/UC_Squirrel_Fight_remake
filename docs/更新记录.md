## 2026-10 第三十三批（`需求147`）：套装收益第二轮 —— 对手也吃、橙档 = 紫 ×1.5、整体加强

**用户口径**（四条）：① 改成**对对手生效**，但挑战塔与无尽塔除外；② 诅咒套增强（蓝 +15% / 紫 +20% 伤害）、
狂战吸血削到 10%、**蓝套及以上生命上限 ×5**、忍者闪避（蓝 +5% / 紫 +8%）；③ 橙套收益应当是**紫套 ×1.5**；
④ 全表强度再 ×1.5（用户选定「先按第②条写、再全表 ×1.5」）。

- **对手也吃（塔除外）**：套装收益的落点从「玩家专用」扩到 `State.genAI` 造出来的所有对手
  （挑战 / 竞技场 / 天梯 / 好友切磋）。**挑战塔与无尽塔不受影响** —— 那边走 `tower.js` 的 `buildFoe`
  （按层数曲线造敌人，套装只用来决定外观 `wearsOf`），根本不经过 `genAI`。
  实测：对手**带套装收益的比例**按等级为 81%(低等级) / 48% / 41% / 37% / 32%，且几乎只吃到 2 件档
  （4 件档 ≤0.5%）—— 对我方胜率的影响是 **−0.2 ~ −1.7pt**，属于「有感但不改难度」的量级。
- **橙档 = 紫档 ×1.5**：品质系数 0.5 / 0.75 / 1 / 1.3 / **1.95**（原橙档 1.6）。
  橙装是三件紫装融出来的顶级档，1.5 倍才对得起成本；**橙档要求四件全橙**（整套按最低品质算）。
- **全局强度系数**：新增 `SET_BONUS_GLOBAL_MUL = 1.5`，乘在品质系数之后 ——
  以后要整体调强/调弱只动这**一个数**，表里的基础值保持整数好读。
- **第②条落表**：诅咒伤害 2 件 6% + 4 件 9% = 基础 15%（×1.5 → 蓝 22.5% / 紫 29.3%）；
  忍者闪避 2 件 2% + 4 件 3% = 基础 5%（×1.5 → 蓝 7.5% / 紫 9.8%；紫档按系统的 ×1.3 走，
  所以不是用户写的 8%——要紫档严格 8% 得把基础写成 6.15%）；
  狂战吸血基础 5%（×1.95 橙档系数 = 9.75% ≈ 10%，×1.5 → 14.6%）。
- **生命上限：先按 ×5 试，实测顶穿后按用户改判落到 ×2**。生命乘数抽成 `SET_BONUS_HP_MUL`
  （白装家族 `SET_BONUS_HP_EXEMPT` 不吃这条），所以只能动一个数：
  ×5 时紫色一个 2 件档就是 **+78 生命**（≈ 25 级玩家血量 257 的 30%），熊猫/犀牛只穿 2 件
  就有 **+13.9pt**、满套 **+23.1pt**，而挑斗 +2.7pt、诅咒 +2.4pt —— 家族之间彻底失衡。
  改 ×2 后实测：熊猫/犀牛 2 件 +5.8pt、满套 **+14.4 / +14.1pt**，与其余家族（+7.6 ~ +13.6）回到同一量级。

  | 紫装家族平均 | +3.1pt（+1.6） | **+10.6pt**（+5.7） |

  整体抬升主要来自用户要的全局 ×1.5；生命类家族仍是最强的一档，但只高 3~4pt（×5 时高 20pt）。

## 2026-10 第三十二批（`需求146`）：套装收益（**本版新增机制**）

**用户口径**：给游戏加「套装收益」；先查原版有没有可参考的 —— 没有的话自己设计，
要有特色但别太强，让玩家在「极品词条」与「套装收益」之间取舍，收益特征尽量贴合套装名字。

- **原版没有套装收益（先查后做）**：`gearSetMap` 的 `setId` 在原版只用来取使用等级 / 售价 / 品质颜色 /
  贴图序号（`references/orig/GameDict.js`、`player.js` 与 Flash 端 `MainMovie.as:105 getEquips()` 逐条核过，
  加属性时从不数同套件数）。所以这套机制是**按上面的口径自己设计**的，不是照抄。
- **规则**：家族 = 装备名去掉部位后缀（「忍者护额/拳套/服/鞋」就是忍者一套，同名跨品质算同一套）；
  穿满 **2 件 / 4 件**各给一档收益，4 件档**叠加**在 2 件档之上；数值 = 基础值 × 品质系数
  （白 .5 / 绿 .75 / 蓝 1 / 紫 1.3 / 橙 1.6 —— **橙档系数已在第三十三批改成 1.95 = 紫 ×1.5**，狂战按橙计），
  品质取所穿该套里**最低**的那一件。
- **数值表只有一处**：`js/gamedata.js`【GD6】`SET_BONUS`（16 个家族 × 2 档）。改平衡只动这张表；
  界面与帮助的文案由 `setBonusText()` 从数值生成，不会和数值走偏。
- **数值是实测标定的**（配对模拟：25 级随机玩家 vs 23 级随机对手、同一随机流、1000 组）：
  紫装满 4 件约 **+5 ~ +7pt** 胜率、只凑 2 件约 **+1 ~ +2.5pt**、白装家族约 +2 ~ +3pt、
  狂战（50 级传说档）约 **+8pt** —— 量级与「把 4 件装备的 8 条词条全换成想要的」相当，所以才有取舍。
  两条踩到的坑写进了表头注释：① **速度最贵**（+1 速度 ≈ +3pt，+10 力量才 ≈ +4pt），带速度的家族必须很少；
  ② **反伤不能给小数值**（sim 的 `max(1, round(伤害×比例))` 有 1 点地板，1~2% 反伤实测能顶 +6pt），故本表不用它。
- **取舍点**：收益压在「1~2 条好词条」的量级 —— 想要套装收益就得放弃跨套挑词条的自由，反之亦然。
  特征跟着名字走：忍者=闪避、骑士/幕府=减伤、熊猫=回合回复、犀牛=开局护盾、仙鹤=开场强攻、
  螳螂/狂战=低血爆发、诅咒=增伤但受伤也变多。
- **实现口径**：属性类收益并进 `State.totalStats()`（与装备主属性同一条路，一起被色诱之术脱掉）；
  战斗类收益走**独立通道** `fighter.setFx`（`state.js` 的 `applySetBonuses` → `main.js` 的 `startBattle`），
  不复用塔 buff 的 `mods` —— 它本来就是装备给的，也不该吃无尽塔「增幅水晶」的全局倍率。
- **只对玩家生效**（**已在第三十三批改为「对手也吃、塔除外」**）：对手的装备是随机穿的（几乎凑不齐同名），
  挑战塔 / 无尽塔的套装只决定外观（`tower-data.js` 的 `GEAR` / `wearsOf`，数值来自层数曲线），
  所以这条不改变对手强度。
- **界面**：装备页底部一行「当前生效的套装收益」，装备详情里列出该套 2 件 / 4 件两档的**当前数值**与
  生效标记（✓/○），帮助页补一段说明。
- 回归：`tools/test-state.cjs` 的「套装收益 —— 同名 2/4 件两档、按最低品质缩放，且真的进战斗」（`需求146`，一条用例）。

## 2026-10 第三十一批：修「游戏目录永远改不了名 / 移不动」（进程工作目录劫持）

**用户口径**：想把 `E:\松鼠大战怀旧版` 改名成 `Squirrel Fight`，一直提示「文件正在被使用」，
**重启电脑也一样**。要求找出原因并改掉。

- **根因（实测抓到的现场）**：有 5 处把这个游戏目录设为**长期进程的工作目录**。只要有任何
  进程把某目录当工作目录，Windows 就拒绝改名 / 移动该目录（`MoveFileEx` 返回
  `ERROR_ACCESS_DENIED`，资源管理器把它显示成「文件夹正在被使用」）；而**重启也没用**，
  因为开机自启的计划任务「SSDZ Sync」会在登录时、并且此后每 5 分钟一次地重建这样的进程。
  抓到的那一刻：`node.exe PID 52516  cwd=E:\松鼠大战怀旧版  启动于 18:52:01`（正是任务的下一次触发时间）。
- **改掉的 5 处**（都先确认过不依赖工作目录：`sync.js` 只用 `__dirname`、从不调 `process.cwd()`；
  `serve.js` 用 `path.resolve(__dirname, '..')`；其余路径都是 `Join-Path` 拼的绝对路径）：
  ① `scripts/sync/run-hidden.vbs` —— 删掉 `sh.CurrentDirectory = root`（**就是这一行**把 node 的
  工作目录设过去的）；② `sync.js` 生成计划任务 XML 时不再写 `<WorkingDirectory>`（原来自动生成的
  任务里就带着它，所以只改已装的任务、不改代码，会被重新写回去）；③ `sync.js` 里两处
  `spawn(..., { cwd: ROOT })` 去掉 `cwd`；④ `scripts/sync/sync-win.ps1` 去掉 `Set-Location -LiteralPath $root`；
  ⑤ `scripts/start-game.ps1` 去掉 `Set-Location -LiteralPath $root`，否则**一玩游戏，后台服务器进程
  就一直锁着游戏目录**。macOS 的 launchd plist 里同样的 `<key>WorkingDirectory</key>` 也一并去掉。
  每处都留了注释说明原因，避免以后被顺手写回去。
- **有意保留**：`start-game.ps1` 给桌面 exe 的 `-WorkingDirectory $root` 没动 —— 它是 exe「找游戏目录」
  的输入之一（`src-tauri/src/lib.rs` 第 2 条：当前目录上溯），只在游戏窗口开着时占用，属正常行为。
- **改名本身**：本机 DSH 自己的沙箱服务（`CodexSandboxService`，SYSTEM 权限）仍占用该工作区，
  在 DSH 运行期间改不动，所以改名交给一次性脚本 `out/rename-to-SquirrelFight.ps1`
  （+ 双击用的 `out/改名-SquirrelFight.cmd`，自动提权）：能立刻改就立刻改，改不动就登记
  `MOVEFILE_DELAY_UNTIL_REBOOT` 到下次开机（开机时用户程序都还没起，必定成功），并同时把计划任务
  与 DSH 的工作区记录改到新路径。用完即删（`out/` 本来就不进仓库）。
- **回归**：22 个套件全绿（含 `tools/test-sync.cjs`、`tools/check-asset-paths.cjs`）。

## 2026-10 第三十批：一键出包脚本 `tools/build-release.ps1`

**用户口径**：写一个脚本，跑一下就自动完成 exe + 安卓 APK 打包、产物落 `src-tauri\dist`、
删掉上一版本的 exe/apk、删掉 ~10 GB 打包缓存，并支持版本号自动对齐（如 0.4.7）与手动改安装包名。

- **脚本做的事**（六步，每步先体检、失败即停）：① 版本号对齐 → ② 精确删掉 `dist` 里本次不产出的
  exe/apk → ③ 编 Windows 轻壳 exe + NSIS 安装包（转调 `tools/build-tauri-app.cjs`）→
  ④ 编安卓 APK（转调 `tools/build-apk.ps1`，中文路径 / NDK 那些坑沿用它的）→ ⑤ 按名称模板改名落到 `dist`
  → ⑥ 删 `target\` / Gradle `build\` / `web\` 等打包缓存。
- **不重复造轮子**：真正编译的两步还是原来那两个脚本，这里只做编排、改名、清理与体检，
  所以 build-apk.ps1 里那些绕坑的注释依然是一手依据。
- **参数**：`-Version 0.4.7`（不给就 patch+1）、`-NoBump`、`-DryRun`、`-SkipExe/-SkipInstaller/-SkipApk`、
  `-Name`（基名）+ `-ExeName/-InstallerName/-ApkName`（模板，占位符 `{name} {version} {abi} {arch} {date}`）、
  `-Abi`、`-DebugApk`、`-KeepCache`、`-CleanOnly`、`-DeepClean`（连 `~\.gradle\caches` 一起清）。
- **踩到的两个本机坑**（都写进脚本注释了）：
  ① 这台机器**只有 Windows PowerShell 5.1，没有 pwsh** —— 重入调用安卓脚本必须用 `$PSHOME` 里的
     `powershell.exe`，写死 `pwsh` 会直接找不到命令；
  ② `.ps1` 里带中文**必须存成 UTF-8 with BOM**（`build-apk.ps1` 本来就是 BOM），否则 5.1 按 GBK 读、
     整个脚本语法都散架；另外 5.1 的 `ConvertTo-Json` 会把中文转义成 `\uXXXX`，所以 `version.json`
     改成「只替换 version/commit/date 三个值」的正则改法。
- **版本号一共六处**，脚本一起对齐（`Cargo.toml` / `Cargo.lock` 的 `ssdz-classic` 块 / `src-tauri/package.json`
  / `tauri.conf.json` / `version.json` / `gen\android\app\tauri.properties` 的 `versionName` + `versionCode`）。
  安卓那份 `versionCode` 用 Tauri 的算法 `major*1000000 + minor*1000 + patch`（0.4.6 → 4006、0.4.7 → 4007，
  已在打出来的 APK 上用 `aapt2 dump badging` 核对过 `versionCode='4007' versionName='0.4.7'`）。
  `tauri.properties` 在 gitignore 里但**是 build-apk.ps1 同步到 ASCII 副本的真源**，不改它会留下版本不一致。
- **实跑暴露并修掉两个真 bug**（这种问题只有真打一次包才看得见，`-DryRun` 都发现不了）：
  ① **清缓存清单是打包前扫的** —— `target\` 是这次编译才生成的，照着旧清单删等于全漏。
     首次实跑只释放了 84.6 MB，实际漏掉 6.17 GB；改成在 BR7 **打包后重新扫描**后释放 6.24 GB
     （`src-tauri\target` 2.52 GB + 安卓 target 2.59 GB + Gradle `app\build` 1.07 GB + …）。
  ② **`-CleanOnly` 没有真的"只清缓存"** —— 它照常跑完两套编译，而且因为 `$want` 为空，
     差点把 `dist` 里现有的产物当"上一版本的旧包"删掉。现在 `-CleanOnly` 会强制跳过三个 `-Skip*`
     并一律不动 `dist`；末尾补 `exit 0` 让退出码稳定（之前会漏成 1）。
  ③ **清理清单里不该有 `src-tauri\gen\schemas`** —— 它写在 `.gitignore` 里，但那 4 个 json
      其实**是入库的**，删掉会让仓库多出 4 个 `D`（实测踩到，已 `git checkout` 恢复，并把它
      从清单里移除、加了注释）。
- **顺带修掉自己的一个隐患**：`[regex]::Replace($t,$p,$sb,1)` 的第 4 个参数是 **RegexOptions** 不是
  「替换次数」，传 1 等于「忽略大小写 + 替换全部」。脚本改用实例重载 `Regex.Replace(input, evaluator, 1)`
  并抽成 `Replace-First`，已单测（`Cargo.toml` 里依赖的 `version = "2.0.1"` 不会被误改）。
- **实测结果**：0.4.6 → 0.4.7，`src-tauri\dist` 出三样 ——
  `squirrel_fight.exe` 2.9 MB / `squirrel_fight_0.4.7_x64-setup.exe` 66.1 MB /
  `squirrel_fight_0.4.7_arm64-v8a.apk` 146.2 MB；0.4.6 那两个旧包（146.1 MB + 66.1 MB）自动删除；
  打包缓存 6.24 GB 自动清掉。全流程第一次 6 分 37 秒（含冷编译），热编译约 3.5 分钟。
- **回归口径**：这是构建脚本，没有进 `test-*.cjs`；验证方式是 `-DryRun` 打印计划 + 真实出包 + `-CleanOnly`。
  改完 22 个套件仍全绿。

## 2026-10 第二十九批：修装备融合界面（规则条炸版 + 装备列表被挤没）

**用户口径**：融合界面的介绍乱成一团，要大量精简，并保证装备正常显示。

- **病根**：`.fusion-rules` 是 `display:flex` 的一行容器，上一批把整段说明连 `<br>` 塞了进去 ——
  flex 会把每段文字拆成**独立的 flex item**，规则条直接变成 7 条竖排文字；
  同时规则条撑满纵向空间，把 `flex:1 1 auto` 的装备列表压到高度 0，**装备卡整片消失**。
- **修法**：
  ① 规则条只留一句话（`flex` + `nowrap` + 省略号，永远撑不破），完整说明搬进
  「详细规则」弹窗（`classic-fusion.js` 新增【FS3】`showRules()`，百分比仍从 `State.FUSION_*` 取，不会和代码脱节）；
  ② `.fusion-inventory-panel` 加 `min-height:150px` 硬底线，装备列表再也不会被上方压没；
  ③ CSS 里写清「别在这里塞 `<br>`」的注释，`.fusion-help` 样式新增。
- **验证**：headless Chrome 渲染真实 markup + 真 CSS，逐张核对初始态 / 已放入 3 件同名紫装态 /
  详细规则弹窗，3 倍图确认装备卡图标、品质缎带、状态带、名字都正常。
- **回归**：`tools/test-fusion.cjs` 新增「规则条保持单行且完整说明收在弹窗里」
  （断言无 `<br>`、文案 ≤60 字、有详细规则入口、5 个字段齐全、装备卡仍渲染）。22 个套件全量通过。

## 2026-10 第二十八批：融合再加两条规则（同名变异狂战 / 共有词条继承）

**用户口径**：2 同名与 3 同名合成高档装备时，大概率出同名、小概率变异成狂战；
属性方面「2 条以上一样的保留、概率升星，没有 2 条就随机」。

## 2026-10 第二十六批（`需求145`）：原地重画系统页不再弹回页首

- **用户反馈**：在系统页点「把存档送过去」或「检查更新」时，页面会自动跳回最上面。
- 根因：系统页内容比底板高（滚动容器是 `.classic-board` 的 `overflow-y:auto`），
  而这些动作都要重画整页（`openSystem()` → `page()`），新页面挂上去后 `scrollTop` 归零。
- 修法在 `page()` 里统一处理：重画前记住**同一 data-screen** 的旧 board 的 `scrollTop/scrollLeft`，
  新页面追加完成后放回去。换页（首页 → 系统页之类）时旧 board 的 `data-screen` 不匹配，
  天然从 0 开始；其它会重画的页面（如帮助页）也一并受益。
- 回归：`tools/test-ui-flow.cjs` —— 把**真实的 `page()`** 切出来配最小 DOM 桩，
  断言「同一页重画后 scrollTop 不变（中段与到底都测）」「换页与首次进入从 0 开始」。
  该用例已验证：临时关掉恢复逻辑时它会红。
