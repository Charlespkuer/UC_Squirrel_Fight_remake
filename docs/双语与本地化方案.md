# 双语（本地化）方案：可行性、结构、迁移计划

> 结论先说：**能做**，而且这个项目比一般项目更好做（界面全是字符串拼 `innerHTML`，
> 换语言只要重画一次；没有框架、没有构建步骤）。难点不在技术，而在**体量**：
> 现在有约 **3200 条中文字面量**、**1700 处拼接**、**6400 处测试里的中文断言**。
> 所以正确做法不是「一次性全翻」，而是**先立骨架 + 单页试点，再按界面分批迁移**，
> 未迁移的文案自动回退中文 —— 任何时刻游戏都能玩、都能发布。

---

## 1. 体量盘点（2026-10 实测，脚本口径见文末）

| 指标 | 数量 | 说明 |
|---|---|---|
| `js/` 里含中文的行 | **5951 / 21416**（17 个文件） | 界面文案 + 数据文案 + 注释。注释不需要翻 |
| 中文字符串字面量 | **≈ 3241** 条 | `classic-ui.js` 721 / `tower-ui.js` 569 / `tower-data.js` 416 / `tower.js` 334 / `state.js` 310 / `debug.js` 228 … |
| 含中文的字符串**拼接点** | **≈ 1686** 处 | 例如 `'第 ' + n + ' 层'` —— 这是本地化真正的成本所在，必须整句模板化 |
| `classic-extras.js` 里的 `\uXXXX` 转义中文 | 2774 个转义（≈1387 汉字） | 该文件把中文写成了转义，抽取脚本必须一起处理，否则会漏一整屏文案 |
| 静态数据里的中文名（`gamedict.js`） | 360 行 | 武器 / 技能 / NPC / 道具名，属于「数据」，要用本地化覆盖表而不是改数据 |
| `scripts/index.html` | 8 / 56 行含中文 | 很少，顺手就能处理 |
| `tools/*.cjs` 里的中文断言 | **≈ 6400** 处 | 大量「源码里必须有某句中文」的守卫，迁移时会大面积变红（见 §7） |
| `docs/*.md` | 约 3000 行 | **不翻**（开发者文档），只翻游戏内文案 |

## 2. 推荐结构：每种语言一个「文件包」

```
js/i18n.js                    # 运行时：t() / 插值 / 回退链 / 语言切换
locales/zh-CN.js              # 中文包（基准，永远是完整的）
locales/en.js                 # 英文包（允许缺 key → 回退中文）
locales/zh-CN.data.js         # 数据层覆盖表：buff 名/描述、武器技能名、NPC 名…
locales/en.data.js
tools/i18n-scan.cjs           # 抽取：扫描源码 → 待翻译清单（含 文件:行 + 上下文）
tools/i18n-build.cjs          # 打包：locale json → js（避免运行时 fetch，file:// 也能跑）
tools/test-i18n.cjs           # 校验：key 完整、占位符一致、无遗漏中文（白名单逐步收紧）
```

`js/i18n.js` 的接口（刻意做得很小）：

```js
I18n.locale            // 'zh-CN' | 'en'
I18n.setLocale('en')   // 切换 + 落存档（S.lang）+ 通知界面重画
I18n.t(key, params)    // t('tower.layer', { n: 3 }) → '第 3 层' / 'Floor 3'
I18n.pick(zhText)      // 以中文原文为 key 的过渡用法（见 §3）
I18n.nameOf(kind, id)  // 数据层：武器 / 技能 / NPC / 道具名
I18n.descOf(buff, mode)// 数据层：buff 描述（给 tower-data.descOf 用）
```

`locales/zh-CN.js` 就是**唯一的中文事实来源**：

```js
I18n.addPack('zh-CN', {
  'ui.home.bag': '道具',
  'ui.home.status': '状态',
  'ui.system.support.title': '支持作者',
  'ui.system.support.body': '这个复刻版完全免费：没有内购、没有广告。',
  'tower.layer': '第 {n} 层',
  'tower.battle.of': '第 {n}/{total} 场',
  'buff.stack.max': '最多叠 {n} 层',
  ...
});
```

**key 命名规则**（建议固定下来，不然几千个 key 会乱）：
`<区域>.<页面/模块>.<元素>[.<变体>]`，例如 `tower.endless.shop.title`、`battle.result.win`、
`buff.C26.desc`。区域只用 `ui / battle / tower / endless / stage / system / buff / data` 这几个。

## 3. 三种接入方式，以及为什么建议「混合」

| 方式 | 写法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 语义 key**（主推） | `I18n.t('ui.home.bag')` | 稳定：改中文文案不丢翻译；可做完整性校验 | 要人工起 3000 个 key 名 |
| **B. 中文原文当 key**（过渡） | `I18n.pick('道具')` | 迁移最快：`pick()` 直接把中文当 key 查表，查不到就原样返回 | 中文一改就断链；两处同句无法区分语境 |
| **C. `data-i18n` DOM 属性** | 渲染完统一替换 | 适合静态 HTML | 本项目 95% 是模板字符串拼出来的，收益很低 |

**建议**：A 为长期形态，B 作为**迁移期的自动兜底** —— 实现上就是 `I18n.t()` 在 key 未命中时，
再去 `zh-CN` 包里按「文案原文」找一次；这样即使某处只从 `'道具'` 改成 `I18n.pick('道具')`，
英文包也可以只翻常用的那批，其余原样显示中文（不报错、不空白）。

对本项目还有两条必须写进规范的约束：

1. **禁止再写拼接**：`'第 ' + n + ' 层'` 一律改成 `I18n.t('tower.layer', { n })`。
   语序在英文里会反过来（`Floor 3` vs `3 层`），拼接一定出事。
2. **数字与列表**：`num()` / `setNum()` 已经统一处理数字贴图；英文包要决定
   「1,234」还是「1234」、复数（`1 layer` / `3 layers`）用 `{n, plural}` 之类的小工具解决。

## 4. 数据层（buff / 武器 / 技能 / NPC）怎么处理

**不要动 `gamedict.js` 与 `tower-data.js` 里的中文数据**（它们是原版数据与数值定义，
测试、平衡脚本、存档都按 id 引用）。正确做法是**在展示层加一层覆盖表**，而这一层的
「单点」在这个项目里已经存在：

| 出口 | 现状 | 本地化改法 |
|---|---|---|
| `TowerData.descOf(buff, mode)` | 已被卡面 / 商店 / 集锦 / 调试台共用（第十九批又加上了叠层说明） | 改成 `I18n.descOf(buff, mode)`：英文包按 `buff.<id>.desc` 查表，缺就回退中文 |
| `TowerData.RARITY_NAME` / `SCOPE` / `KIND_LABEL` | 稀有度、限次/永久/即时 | `I18n.t('rarity.3')` |
| `gamedict` 的武器/技能/NPC/道具名 | 通过 `weaponInst()` / `skillInst()` / `propMap.getValue().name` 使用 | 加 `I18n.nameOf('weapon', id)`；**存档只存 id**，所以换语言不影响存档 |
| 英雄/NPC 的 `mechDesc`、环境词缀 `name/desc` | 由 `envText()` / `entryInfo()` 生成 | 同上，按 id 查表 |

存档里会留下少量**历史中文快照**（`run.pendingToasts`、`lastSacrifice.name`、
`run.buffLog[].detail`），换语言后这些旧提示仍是中文 —— 可以接受（一次性文本，重开对局即消失）。

## 5. 迁移计划（分四步，每步都能单独发布）

| 阶段 | 内容 | 可见成果 | 量级 |
|---|---|---|---|
| **P0 骨架（1 天）** | `js/i18n.js` + `locales/zh-CN.js` + 抽取/校验脚本 + 设置页语言下拉 + `S.lang` 落存档 | 语言可切换，但界面还是中文（因为包就是中文） | ~300 行 |
| **P1 高频界面（3~5 天）** | 主界面 / 系统页 / 提示弹窗 / 主菜单 / 战斗结果 / 挑战塔与无尽塔的**框架文案**（标题、按钮、标签） | 切英文能玩：看得到全部按钮与主流程 | 600~900 条 |
| **P2 机制长文案（5~8 天）** | buff 描述（104 条）、武器/技能说明（37 条）、NPC 机制、环境词缀、帮助页 | 英文玩家能读懂数值与机制 | 900~1200 条 |
| **P3 收尾（2~3 天）** | 剩余杂项（debug 面板可保持中文）、`data-i18n` 小段静态 HTML、字体/换行适配、CI 增加 `test-i18n` | 全绿 | 300~600 条 |

**最小可用建议**：只做 P0 + P1 + P2 里「高频的 300~500 条」，其余回退中文。
这样投入产出最高，也不会因为「翻了 30% 却到处夹中文」而显得半成品
（回退策略要写进 UI 规范：缺翻译显示中文，而不是显示 key）。

## 6. 运行期细节（这个项目特有的几个坑）

1. **语言检测**：`navigator.language`（WebView / 浏览器 / 安卓都可用）。Tauri 想要系统语言
   更精确可以加 `tauri-plugin-os`，但没必要 —— `navigator.language` 已经够用。
2. **切换后重画**：界面全是 `innerHTML` 重绘（`renderHome()` / `openTower()` / `openEndless()`…），
   所以 `setLocale()` 只需要「落存档 + 调一次当前页面的 render」。
3. **`file://` 与安卓打包**：locale 必须是 **js 文件**（`<script>` 引入），不要用 `fetch('locales/en.json')`
   —— 安卓前端嵌在包里、`file://` 也会被 CORS 挡。
4. **字体度量**：英文普遍比中文长 30~60%，按钮/卡片会溢出。要么给这些容器
   `white-space:normal` + `max-width`，要么英文包刻意用短词（`Bag` 而不是 `Inventory`）。
   建议在 P1 一次性过一遍所有固宽按钮（`.uc-button`、`.home-menu`、塔底操作条）。
5. **canvas 里的文字**：本项目文字几乎都是 DOM；如果哪张图/哪处 canvas 画了中文，
   需要按语言出两套资源（先扫一遍 `drawFightBack` / 飘字相关代码确认）。
6. **图片里的文字**：`images/classic/**` 里如果有烘焙的中文（例如某些牌子、按钮贴图），
   要么换成无字版 + CSS 文字，要么出两套图。这一项要在 P1 之前先扫一遍，可能是唯一的硬骨头。
7. **`classic-extras.js` 的 `\uXXXX`**：抽取脚本必须解码 `\uXXXX` 再写进清单，
   否则这个文件（约 20 屏周边系统）会整体漏翻。

## 7. 测试与 CI 的迁移（这是最容易被低估的一块）

现在 `tools/test-*.cjs` 里有约 **6400 处中文**断言，其中很多是**源码守卫**
（`assert.match(src, /支持作者/)`）与文案断言（`assert.match(b.desc, /最多 3 层/)`）。
建议按下面的顺序改，避免「迁移一半 CI 全红」：

1. **文案断言 → 数据断言**：能断言字段就断言字段（`maxStacks === 3`、`uses === 3`），
   不要断言界面上的中文；界面文案改到 `test-i18n.cjs` 里按 key 断。
2. **源码守卫 → key 守卫**：`assert.match(src, /支持作者/)` 改成
   `assert.ok(pack['zh-CN']['ui.system.support.btn'])`。
3. **`test-i18n.cjs` 的三条硬规则**：
   - `zh-CN` 必须覆盖所有被 `t()` 引用的 key（英文可以缺，缺的列出来但不失败）；
   - `t()` 的 `{}` 占位符在两边必须一一对应；
   - 白名单外**不允许**再出现中文字面量（白名单按文件/行逐步收紧，先全绿再逐步加严）。
4. `tools/test-buff-tags.cjs` 之类用 `fs.readFileSync('js/tower-data.js')` 做正则校验的脚本，
   注意它们读的是**源码**，迁移到 i18n 后要跟着改口径（数据还在，文案搬走了）。

## 8. 工作量与收益评估

- 纯抽取 + 建骨架：**1~2 天**（有脚本，是机械活）。
- 中文包落地（把现有文案搬进 `zh-CN`）：**5~10 天**，与 P1/P2 合并进行；
  **这一步没有任何玩家可见变化**，但它是后面所有工作的地基。
- 英文翻译：取决于翻译质量要求，**机器初翻 + 人工过一遍高频 500 条 ≈ 3 天**；
  全量人工 ≈ 2 周。
- 长期成本：新增文案必须在 `zh-CN` 和（至少）`en` 各加一条 —— 这是唯一需要写进
  贡献规范（`CONTRIBUTING`）的约束。

**我的建议**：先让我落 P0（骨架 + 抽取/校验脚本 + 设置页语言开关 + 一个新页面做试点，
比如刚做的「支持作者」弹窗），你确认结构与 key 风格之后，再按 P1→P2 批量迁移。
这样风险最低：任何阶段都可以停，游戏始终可玩、测试始终可绿。

### 附：本文的统计口径（可复现）

```bash
# 含中文行 / 字面量 / 拼接点 / \u 转义（脚本在 /tmp，可随时重跑）
node -e "…扫描 js/*.js 的 /[\u4e00-\u9fff]/ 与 /'[^']*[\u4e00-\u9fff][^']*'/g…"
```

- 字面量统计：只算单引号字符串与模板字符串（`'…'`、`` `…` ``），注释与文档不计。
- 拼接点：`'中文…' +` 与 `+ '中文…'` 两种模式各计一次，所以会略高于实际「必须改」的数量。
- 测试断言：`tools/*.cjs` 里同时含 `assert.` 与中文字面量的行（粗略，用于估量级）。
