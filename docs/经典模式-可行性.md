## 1. 已确认口径（用户 2026-10-13 拍板）

| 维度 | 决定 | 含义 |
|---|---|---|
| **忠实度** | **版式复刻 + 现代适配** | 沿用原版版面结构、九宫格边框、按钮/图标切图、配色与字体；**保留**现有的鼠标操作、滚动与自适应缩放。不做像素级 1:1，不搬键盘导航。 |

## 2. 几何与坐标基础

| 对象 | 尺寸 | 长宽比 | 说明 |
|---|---|---|---|
| Flash 舞台 | **320 × 196** | 1.6327 | 直接解析 `references/ssfight/viewer/game/ssfight-local.swf` 头部 RECT 实测；14 fps / 110 帧 / Flash 7 / AS2 |
| 安卓版首页背景 `main.jpg` | **868 × 512** | 1.6953 | 见 §3 |
| 复刻**菜单页**空间 | **1170 × 712.174** | 1.6429 | `js/main.js:61` 的 `W * 560 / 920`；由 `css/classic-refine.css:2` 的 `.classic-page{top/bottom:-11.087px}`（690 + 2×11.087）撑出 |
| 复刻**画布**空间 | **1170 × 690** | 1.6957 | 战斗 / 首页场景（`js/main.js:22-23`） |

换算：

```
菜单页 ← Flash 舞台：横向 ×3.65625 (1170/320)、纵向 ×3.63354 (712.174/196)   ← 差 0.62%
画布   ← 安卓 main.jpg：横向 ×1.34793 (1170/868)、纵向 ×1.34766 (690/512)     ← 基本等比
```

**三条必须钉死的结论**：

1. **菜单页与画布是两个不同参考系**，这是刻意设计（`css/classic-refine.css:1` 的注释
   `Classic pages keep the reference 920:560 ratio; combat keeps 1170:690.`）。
   后果：**同一颗 `.uc-button` 在首页（690 空间）与分页（712 空间）里的视觉尺寸不一致**
   （`css/classic-refine.css:61` 甚至专门给 `.home-menu .uc-button` 写了 `font-size:47px`）。
   经典模式开关**必须先钉死"菜单页用哪套高度"**，否则同类按钮在不同屏上大小不一。
2. **"920:560"这个参考比例（1.64286）把原版的 320:196（1.63265）压扁了 0.62%。**
   做严格坐标对齐时要选口径：**(a) 严格等比** → 高度应为 `1170 × 196/320 = 716.625`，坐标一律 ×3.65625；
   **(b) 沿用现状** → 保留 712.174，横 ×3.65625 / 纵 ×3.63354。
   **推荐 (b)**：改高度会牵动 `css/classic-refine.css:2` 与 `js/main.js:61` 整条缩放链，收益只有 0.62%。
3. **画布（战斗/首页场景）不是 Flash 的比例**。要把战斗也做成 Flash 版式就得**重排战斗场景**，
   工作量远超其余所有屏之和。**建议排除**（§11 第 2 条）。

### 3.1 运行时现在用的是哪一种？——**是混血**

**已核实的两个事实：**

| 事实 | 证据 |
|---|---|
| **首页背景是写实重绘**（不属于 Flash 版画风） | `images/ui/screens/main.jpg`（868×512，画着 "Big Tirbe" 蘑菇屋 + 多层植被光照）；由 `js/main.js:277-281` 加载并**默认加 `blur(1.1px)` + 白纱**（`js/main.js:34-53`，注释自陈"原版 main.jpg 细节很密，HUD 与角色压上去会互相抢"）。它来自**安卓版资产清单**：`references/orig/asset2.js:8 {id:"main",src:"images/main.jpg"}` → `js/gamedict.js:651` |
| **UI 切图是扁平卡通的、并且是从原版截图恢复的** | `images/ui/buttons/{return-menu,change-equipment,status,weapon,skill}-{active,normal}.png`（扁平卡通胶囊，786×192 等 2× 尺寸）；`images/ui/home/{activity,chat,village}.png` 与三张中间裁切 `references/screen/_tmp_{activity,chat,village}_region.png` **一一对应** —— 证明这批切图是**从原版截图裁出来再修干净的**。接线上：`js/classic-ui.js:49` 的 `buttonArt`、`css/classic-refine.css:119-122`、`js/classic-ui.js:477` 的浮标 |

**所以现状是**（这条结论决定整个方案的性质）：

> 复刻的**界面控件、图标、卡牌、角色立绘**（胶囊按钮、Tab、浮标、位图数字、武器/技能/道具/装备图标、
> 卡牌、松鼠与 NPC 立绘）**已经全部来自原版截图 / 安卓图集的裁切，本来就是扁平原版观感**；
> **只有背景与场景美术**（首页 `main.jpg`、胜负 `win.jpg`/`loss.jpg`、战斗背景 `fightBg_*`、场景特效）
> 来自**安卓客户端的写实重绘**。
> 因此"经典模式"主要要换的是**背景与场景美术**，以及**补齐原版范式里被改掉/漏掉的细节**（§4），
> 而不是"把界面重画一遍"。**逐层来源见 §3.2 的实测表（P0-a 已完成）。**

**§4.1 #2 结论（2026-10-13 修正，含一次自我纠错）**：

- 本表原写"占 **26% × 31%**、比原版小约 1/3"—— **高度那一半是错的**。实测（改动前）：
  包围盒 333×340、`k = min(490/333, 307/340) = 0.9026` → 绘制 **301 × 307**，
  即 **宽 25.7% × 高 44.5%**。**高 44.5% 本来就已经等于原版的 ~45%**（box 高 307 就是屏高 44.5%，
  而 contain-fit 在这里是**按高度顶满**的）。原来记的"31%"大概是拿某一帧蜷缩姿势的可见像素量的。
- 真正的浪费在**宽度**：量包围盒时把贴地的 `54`（210×54，位于脚下方 y 573~627，而身体只到 571）
  一起算进去了，把包围盒往下拽了 ~56px，于是按高度算出的缩放白白小一圈。
- **修法**：`js/classic-ui.js:552` 的 `exclude` 由 `['75','20001']` 改成 **`['54','75','20001']`**
  —— `battle.js:302` 对同一批元素用的就是 `['54','75','91']`，**保持项目内一致**；
  它只影响"量尺寸"，不影响绘制（`drawFrame` 没传 exclude，影子照画）。
- **改后实测**：包围盒 333×**284**、`k = 1.0798` → 绘制 **360 × 307** = **30.7% × 44.5%**，
  **宽度 +19.6%**，且高度仍精确顶满 box（不溢出）。
- **与"~40% 宽"仍有差距，但那是范式差异、不是缩放 bug**：复刻是**对动画包围盒 contain-fit**
  （尺寸随跑动范围浮动），原版是**固定缩放**画 `myself`（精灵 6988，`ma` 缩放 0.5834；
  sprite 内容框 446×304 → 换算到 320×196 舞台是 **x 49.1~309.3、y 5.9~183.3**，

**§4.1 #3 结论（2026-10-13 修正，含一次自我纠错）**：

- 本表原先写的"原版间距**不规则**（53.6 / 73.45 / 62.5 / 69）"是**看错了对象**：那四个数是
  **相邻按钮原点（`ma` 的 `tx`）之差**，而按钮**宽度不同**（53 / 52 / 82 / 52 / 52），所以
  **边缘之间的缝隙其实几乎等宽（4.34 / 4.30 / 3.77 / 4.59）**。真正"不规则"的是**宽度**
  —— 主按钮「开始挑战」是其余按钮的 **1.58 倍**宽。
- 本表原先写的"复刻两份数据都不符"里，**DOM 那组 `6.0/69.3/132.6/216.6/279.9` 是纸上算错的值**。

## 5. 「经典模式」的三种定位（请拍板）

| 定位 | 内容 | 观感差异 | 工作量 | 与"版式复刻+现代适配"口径 |
|---|---|---|---|---|
| **A. 换素材** | 只把**写实重绘的背景/角色/场景**换成 Flash 版扁平原版；UI 骨架不动 | **大**（这是玩家一眼可见的差异） | 中 | 符合 |
| **B. 换素材 + 对齐范式（推荐）** | A + 把 §4 已核实的偏差逐条改回原版（融合按钮归位、Exp 百分比、滚动公告、主角放大、关掉背景模糊、消息页 tab/图章/底部、升级改整帧、装备页改整页） | **最大** | 中大 | 符合 |
| **C. A + B + 原版交互** | 再搬键盘导航、热区、无滚动翻页 | 最大 | **大** | **与"保留鼠标/滚动"冲突，不建议** |

## 6. 技术方案

### 6.1 三个候选

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|

#### 6.2.3 ✅ 经典模式换上原版按钮 / Tab 皮肤（2026-10-13）

`images/ui/skins/` 里那 5 张图**一直没被任何 js/css 引用**（而 `README.md:132` 又把 `skins/` 算作
`images/ui/` 的一部分）。本轮查明它们是**从原版截图里裁出来的按钮切图**，而且**已经把字去掉了**
—— `images/classic/reference-details.json` 的 `skins/*` 逐条记着出处与手法
（`method: "Original button skin; source text region filled from unoccluded neighbouring pixels on each row."`）：

| 皮肤 | 取自 | 用途 |
|---|---|---|
| `menu-green.png` (269×189) | `屏幕截图 …161746.png`（村庄页） | 首页底栏那五颗 |
| `tab-green.png` / `tab-gold.png` (348×105) | `…161800.png` / `…162315.png` | Tab：选中 / 未选中 |
| `tab-cream.png` (351×105) | `…162341.png` | 浅色次按钮、禁用态 |
| `return-gold.png` (532×143) | `…162315.png` | 宽的金色主按钮 |

**实现**（全在 `css/ui-mode.css`，**不改 JS**）：用 `border-image` 九宫格 —— 左右取 52px 圆头
（`return-gold` 取 71px）、中段横向 `stretch`，这样圆头不会被拉成椭圆；再配
`box-sizing: border-box` 让这两条边**吃进既有宽度**，不改动原来的布局尺寸（底栏是 grid 定宽的，
撑开就错位）。

**只作用于大按钮**：`.small` / `.tiny`（37~47px 高）塞不下 52px 的圆头，硬套会切坏图形，保持原 CSS。

**踩到并记下的两个坑**（都写进 CSS 注释了）：

1. **具体度**：基础规则 `html[attr] .uc-button:not(.small):not(.tiny)` 是 **(0,4,1)**，而
   `html[attr] .uc-button.gold` 只有 **(0,3,1)** → 主按钮会被基础规则刷成绿的，**光调文件顺序没用**
   （CSS 先比具体度）。修法：金皮/浅皮规则也补上 `:not(.small):not(.tiny)`。
   > 这个坑第一版真踩了：截图里「开始挑战」是绿的，改了「排除 `.home-menu`」还是绿的，才发现是具体度。
2. **底栏主按钮**：`.home-menu` 那条规则选择器很长（(0,6,1)），必须 `:not(.gold)`，
   否则同样会把「开始挑战」刷成绿皮。

**实测**（对比图 `out/classic-layout/compare-skins.png`，三格：现代首页 / 经典首页 / 经典状态页）：
经典模式下首页底栏五颗变成原版绿皮、**「开始挑战」仍是唯一的橙色主按钮**
（`btn('开始挑战','challenge','gold')`，`js/classic-ui.js:477`）；状态页三个 Tab 变成未选中金皮 +
选中绿皮，**叠在 Tab 条上的层次与原版截图一致**。两种模式 `window.__errs` 均为空、无布局错位。

### 12.6 ✅ 村庄页动画已激活（2026-10-13）：松鼠与背景徒弟都动了

**问题**：第一版渲染器只有 `gotoAndStop`，所有元件停在自己的第 1 帧 ——
主角松鼠（`myself` = 精灵 6988，**89 帧**）与背景徒弟（6941/6961/6981，**31/56/91 帧**）全是静帧。

**原版机制**（对反编译与导出数据逐条核实，不是猜）：

| 结论 | 证据 |
|---|---|
| 原版**没有"动画系统"**：每个 MovieClip 默认按舞台帧率（`Fr`=14fps）**自动循环播放**；`myself` 整棵子树 **0 个帧动作** | 逐条扫 `6988`/`6982` 及其全部子孙的 `Sf`，`ac` 字段 0 命中；`showMain()` 对 `myself` 零引用 |
| `gotoAndStop` 只停**自己**，不影响子元件 | Flash 原生语义；`showMain()` 只对 `prentices`/`expMc`/`energyMc`/`point`/数字位/`newMessage` 调它 |
| 父 clip 走帧**不重置**子 clip 的播放头；只有该深度被 `rp` 替换 / 换元件才是新实例 | Flash 原生语义；`myself` 的流正是"首帧全 rp、之后每帧只带 `ma` 移动"（5629→5626→5607 这类才是换元件） |
| 帧推进时**同深度同 id 的显式 `rp` 是真重置**（播放头归 1），main 页闭包里有 **52 处**（如 6988 的 5188/4950）——不能简单忽略 rp | 全闭包扫描：同 id 重复 rp 52 处、异 id 替换 865 处 |
| `prentices` 不是动画元件，是**徒弟数显示器**：第 1/2/3 帧摆 1/2/3 个徒弟、末帧空；徒弟的"动"来自徒弟子元件自己循环 | `MainMovie.as:9430-9436` + 6982 的 5 帧结构实测 |
| `newMessage` 红点：默认 `gotoAndStop(2)`＝隐藏，服务器说有新消息才 `(1)`；复刻没有推送 → 保持隐藏（**不能让它自己播，两帧来回切会变成闪烁红点**） | `MainMovie.as:9440-9464` |

**等价实现**（`js/ssfight/render.js`，~100 行）：播放注册表 + 全剧一个 `setInterval(1000/14)` 节拍器，
每拍推进所有"播放中且多帧"的 clip；`showFrame` 改成**按深度 diff、同深度同 id 复用实例**
（只更新 `ma`/`opacity`），跨帧携带的放置**剥掉 `rp`**（`placedHere` 标记区分"本帧段真出现"），
同帧重复 `showFrame` 不重建（Flash 里停在原帧不动显示列表）。

**踩过的三个坑**（都已修，注释留在代码里）：

1. `startTicker()` 里调 `stopTicker()` 顺手清了注册表 —— mount 是先建树（注册）再启节拍，
   结果整页只有"节拍启动后才出生"的实例在播，松鼠永远停在第 1 帧。**清表是 mount/destroy 的事，不是启节拍的事。**
2. `buildFrames` 合并快照时把 `rp:true` 无限携带 —— 初始放置的 rp 跟着快照进入每一帧，
   每秒刷新数值时的 `prentices.gotoAndStop(2)` 都变成"替换"，徒弟每秒重置回第 1 帧。
3. 位图数字精灵的"空白位"= 最后一帧（靠流末尾的 `remove` 产生）—— 切帧时**不能丢尾帧**，
   否则清位逻辑失效（第一版 `prune` 误删 `tp:1` 的同类事故，见 `gen-ssfight-ui.cjs` 注释）。
